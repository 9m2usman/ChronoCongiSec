#### P2 — Branch-level relationships

Current state: `branches (id, tenant_id, name, code, status)` exists with `UNIQUE (tenant_id, code)`, but nothing references it. `agents`, `sources` and `memory_records` have no `branch_id`. M3's `AgentRecord` and `SourceRecord` already carry `branch_id: Optional[str]`; M3's `MemoryRecord` does not.

Proposed migration (0004 or later):
1. `branches`: add `UNIQUE (tenant_id, id)` as the parent key for composite FKs.
2. New table `membership_branches`:
   - Columns `(tenant_id, membership_id, branch_id, created_at)`. The PK `(membership_id, branch_id)` makes duplicate assignments impossible.
   - `(tenant_id, membership_id) -> memberships (tenant_id, id) ON DELETE CASCADE`. This needs `UNIQUE (tenant_id, id)` on memberships.
   - `(tenant_id, branch_id) -> branches (tenant_id, id) ON DELETE RESTRICT`. A branch cannot be deleted while people are assigned to it; deactivate it via `branches.status` instead.
   - An index on `(tenant_id, branch_id)` and the tenant_id immutability trigger.
   - Result: a Company A membership can never be assigned to a Company B branch.
3. `agents.branch_id`, `sources.branch_id`, `memory_records.branch_id`: nullable, each with a composite FK `(tenant_id, branch_id) -> branches (tenant_id, id) ON DELETE RESTRICT` and an index. **NULL means company-wide** (PRD Demo 3: "global company knowledge"). No new visibility column and no hierarchy.
4. Tests: one and multiple branch assignments; duplicate assignment rejected; cross-company assignment rejected; cross-company resource branch rejected; NULL (company-wide) accepted; branch-specific resource accepted.

Questions:
- **M3:** should `memory_records` get its own `branch_id`, or should a record inherit its branch from its source or agent? If inherited, what happens when the two disagree? Is "NULL = company-wide" the right meaning for M3?
- **M4:** should "Head Office sees all branches" be a rule in M4's policy (recommended), or should the database model it (for example, a flag on `branches`)? Is a user with no `membership_branches` row limited to company-wide data only?
- **M1:** should the JWT carry the authorized branch ids, or should M4 look them up on each request? (Recommended: look them up, so a revocation takes effect immediately.)
- **M6 lead:** when a branch is removed, RESTRICT or SET NULL? (Recommended: RESTRICT plus deactivation.)

#### P7 — Role and permission source of truth

Current state: `memberships.role` is a free-text string (default `SECURITY_ANALYST`; DOC-005 lists TENANT_ADMIN, SECURITY_ANALYST, AI_DEVELOPER and AUDITOR). Login copies it into the JWT, and `backend/app/core/dependencies.py` compares it with `allowed_roles`. The `roles`, `permissions` and `role_permissions` tables exist, but nothing references or reads them.

Proposed (simple, no new service):
1. **Role names are authoritative** for the MVP. Keep `memberships.role` as the role name and add `CHECK (role IN ('TENANT_ADMIN','SECURITY_ANALYST','AI_DEVELOPER','AUDITOR'))`.
2. `roles` holds the same four names as platform-global rows (`tenant_id IS NULL`), with `UNIQUE (name) WHERE tenant_id IS NULL`. `role_permissions` maps them to `permissions.key` values. A data migration seeds them.
3. Custom tenant roles stay out of the MVP. Later, `memberships.role_id` with a composite FK can replace the CHECK.
4. A role change takes effect at the next login, because the role is stored in the JWT. If it must take effect immediately, M4 re-reads `memberships.role` on each request (this ties into GAP-007, token revocation).
5. The client never supplies a role; it always comes from the membership row.

- **M4:** will authorization use `role_permissions` (permission keys), or keep role-name lists in code? If permission keys, please send the list of keys to seed.
- **M4:** how should a disabled role be handled? (Recommended: no "disabled role" in the MVP; change the membership's role instead.)

#### P8 — PostgreSQL Row-Level Security

Blocked today. Partial RLS would give false confidence, so it is not added.
- In docker-compose, `POSTGRES_USER: amsc` is a **superuser** and owns every table. Superusers always bypass RLS, and table owners bypass it unless `FORCE` is set, so policies would protect nothing for the app connection.
- `session.py` does not set any per-transaction tenant context.

Prerequisites:
1. **M7:** two roles. `amsc_owner` runs migrations and owns the tables. `amsc_app` is `LOGIN NOSUPERUSER NOBYPASSRLS` with DML grants only. The app's `DATABASE_URL` uses `amsc_app`; Alembic uses the owner. This is the same restricted role Day 6 needs.
2. **M6:** every unit of work starts with `SELECT set_config('app.tenant_id', :tenant, true)`. The setting is transaction-local, so it never survives into the next use of a pooled connection.
3. **M6:** on every tenant table, `ENABLE` and `FORCE ROW LEVEL SECURITY`, with a policy `USING (tenant_id = current_setting('app.tenant_id', true))` and the same `WITH CHECK`. A missing setting returns NULL, so no rows match and access fails closed.
   - `tenants`, `users` and the login lookups need a narrow path: a `SECURITY DEFINER` function or a separate auth role, to be agreed with M1.
4. **M1/M2/M3:** the tenant passed to the session must come from the verified JWT context, never from a header. Background workers set their own context for each job.
5. Tests: own-tenant read works; cross-tenant read, insert, update and delete are blocked; no context means no rows; no leak after connection reuse; raw SQL is still restricted.

Questions:
- **M7:** can docker-compose, `.env.example` and CI create the `amsc_app` role? (M6 can supply the SQL.)
- **M1:** how should login resolve `tenants` and `memberships` before a tenant context exists: a SECURITY DEFINER function or a separate role?
- **M6 lead:** should RLS be done together with Day 6, since it is the same role work? Recommended.

## Day 3 — checkpoint snapshot integrity (2026-11-17)

**Plan alignment:** DOC-006 Day 3 assigns M6 the checkpoint snapshot schema and persistence tables. The checkpoint and checkpoint-item tables already existed in the Day 1 schema; this Day 3 increment closes a relational-integrity gap in that existing design without changing the product's checkpoint payload format or introducing a new service.

**Implemented on `feat/m6-schema-governance`:**
- Migration `0005_checkpoint_version_record_integrity.py` (parent `0004`):
  - Adds parent key `UNIQUE (tenant_id, record_id, id)` to `memory_versions`.
  - Adds `checkpoint_items(tenant_id, record_id, version_id)` → `memory_versions(tenant_id, record_id, id)`.
  - Adds an index over the child FK columns.
  - Downgrade removes the index, FK and parent key in dependency-safe order.
- SQLAlchemy metadata updated to include the matching parent unique constraint, composite FK and index.
- Raw PostgreSQL tests in `test_checkpoint_integrity.py` verify:
  - A checkpoint item accepts a version belonging to its referenced memory record.
  - A version belonging to a different record is rejected on INSERT.
  - Re-pointing an existing checkpoint item to another record's version is rejected on UPDATE.
- Schema introspection test verifies the exact three-column FK and PostgreSQL delete action; the general two-column tenant-FK audit explicitly excludes this additional three-column integrity relationship.

**Why this matters:** the existing two-column tenant FKs guaranteed that a checkpoint item and its memory version belonged to the same tenant, but did not guarantee that the version belonged to the *same memory record* stored in that checkpoint item. ## Day 6 — Append-only audit verification and restricted app role preparation (2026-11-18)

Branch: `feat/m6-day6-audit-and-app-role`, created from `origin/main` at `8202f79` (Day 5 PR #11 merged, head `0008`). Upstream removed. Baseline: `pytest backend/tests/database`: 496 passed.

**Approved by the M6 lead:**
1. A hash-chained audit with a per-tenant chain and backfill.
2. Policy decisions immutable except `execution_status`.
3. App role code and temporary-role tests only; no docker-compose or `.env` changes.
4. No RLS in the migration: design and OD only.

**Why**
- DOC-006:187 (M6 Day 6): "Verify append-only constraints on audit events table". Deliverable: audit verification DDL. Exit: "Direct UPDATE/DELETE statements rejected".
- TRD SEC-010.
- TRD section 8 "Append-Only Immutability": `audit_events` **and `policy_decisions`** are permanent forensic records.
- Doc 07:144 and :549: "Append-only/hash-chained audit evidence", "tamper-evident evidence for decisions".
- Weakness found on Day 1–3: the app connects as a superuser/table owner, who can switch triggers off without leaving a trace.

**Built**
- `backend/alembic/versions/0009_audit_hash_chain_and_decision_immutability.py` (revision `0009`, parent `0008`):
  - `audit_events.chain_seq` (1, 2, 3 … per tenant), `prev_hash` and `event_hash`, with `uq_audit_events_tenant_id_chain_seq` and `ck_audit_events_chain_link` (the first event has no `prev_hash`; every later event has one).
  - `amsc_audit_event_hash(...)`: SHA-256 over the previous hash and every audit field, joined with U+001F. NULLs are coalesced so they cannot shift fields. Timestamps are hashed as UTC epoch seconds, so the result does not depend on DateStyle or the session time zone.
  - Trigger `trg_audit_events_chain` (BEFORE INSERT): takes a per-tenant advisory transaction lock, reads the tenant's last event, and fills the three columns. Values sent by the caller are ignored.
  - `amsc_audit_chain_break(tenant_id)`: the first broken `chain_seq` (wrong hash, wrong link, or a gap), or NULL if the chain is intact.
  - `amsc_audit_protection_report()`: one row per check. It confirms that the append-only, chain and tenant triggers are enabled and that every tenant's chain is intact. Usable by M7/CI.
  - Trigger `trg_policy_decisions_permanent`: a decision can never be deleted. `proposal_id`, `decision`, `memory_trust`, `policy_result`, `reasons_json`, `incident_id`, `created_at` and `id` cannot change. Only `execution_status` may change.
  - Downgrade restores the exact 0008 state. The chain columns and their values, the functions and the two new triggers are removed; 0004's triggers stay.
- **One-time trigger pause for the backfill (documented in the migration):** existing audit rows get their chain in `(occurred_at, id)` order per tenant. Writing the new columns on existing rows is an UPDATE, which 0004 forbids. So `trg_audit_events_no_update_delete` is **disabled for the backfill and enabled again right after, in the same transaction**.
  - The backfill only writes `chain_seq`, `prev_hash` and `event_hash`. A test compares every original audit field before and after.
  - If anything fails, the whole migration rolls back and the trigger stays enabled. A test (and proof B) checks that the trigger is enabled after the upgrade.
  - This requires running migrations as the table owner, which is the owner role's job in the split below.
- `backend/app/database/roles.py`: SQL generation only, never executed by the application:
  - `app_role_create_statement(name)`: LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS, with no password (set by M7).
  - `app_role_grant_statements(name, owner_role=None)`:
    - DML on application tables;
    - `audit_events`: SELECT and INSERT only;
    - `policy_decisions`: SELECT, INSERT and `UPDATE (execution_status)` only;
    - nothing on `alembic_version`; TRUNCATE revoked everywhere;
    - default privileges for future tables.
  - `app_role_script(...)` gives M7 the whole script. `APP_ROLE_ATTRIBUTES_SQL` and `TABLES_OWNED_BY_ROLE_SQL` are read-only checks.
  - Role names are validated against `^[a-z_][a-z0-9_]{0,62}$` (no SQL injection through names).
- `AuditEventRepository.append` refuses caller-set chain values and returns the database-assigned ones. `list_recent` orders by `chain_seq`; the new `chain_break()` calls the verification function.
- Test helpers: `create_temp_login_role` / `drop_temp_login_role` with a strict `^amsc_test_role_[0-9a-f]{16}$` guard (same idea as the temporary databases), and `role_dsn`.

**Tests**
- `test_audit_chain.py` (new):
  - per-tenant linked chains; caller values ignored; the hash covers every field;
  - tamper detection: an edited event, an edit with a recomputed hash (caught at the next link), a deleted middle event;

**Problems and fixes**
- `asyncpg.Connection` uses `__slots__`, so the test fixture could not attach the role name to it. Fix: the test reads `SELECT current_user`.
- asyncpg sends typed parameters, so a string for a `timestamptz` parameter is rejected. Fix: `$3::text::timestamptz` in the seed SQL.
- Hashing `occurred_at` as text would depend on DateStyle and the time zone. Fix: `extract(epoch FROM occurred_at)::text`.
- `concat_ws` silently skips NULLs, which could let two different rows hash alike. Fix: `coalesce` on the nullable fields (`prev_hash`, `trace_id`).
- The plpgsql variable `name` in the report function shadowed the `name` type and was confusing. Renamed to `trigger_name`.
- Concurrency of the chain: inserts for the same tenant are serialised by a per-tenant advisory lock (other tenants are not blocked). This is correct under READ COMMITTED, the default. Under REPEATABLE READ/SERIALIZABLE a concurrent insert fails with the UNIQUE violation instead of forking the chain, which is a safe failure.

**Note for the project owner about migration 0004 (no change made; merged migrations are not edited)**
- 0004 creates `prevent_audit_event_mutation()` with `CREATE OR REPLACE` and without the `amsc_` prefix used by the other M6 functions. `CREATE OR REPLACE` would silently overwrite a same-named function.
- Migration 0009 relies on 0004's trigger name `trg_audit_events_no_update_delete` for the one-time pause. Please do not rename it without a new migration.
- 0004's own tests were strengthened on 2026-11-18 (exact SQLSTATE 55000 and unchanged rows).

**RLS design (not implemented; OD-11 and OD-18)**
- Policy per tenant table: `ENABLE` + `FORCE ROW LEVEL SECURITY`, with `USING (tenant_id = current_setting('app.tenant_id', true))` and the same `WITH CHECK`. If the setting is missing, the result is NULL, no rows match, and access fails closed.
- `UnitOfWork` already sets `app.tenant_id` transaction-locally (Day 4), with a tested no-leak guarantee.
- Global tables (`tenants`, `users`, `permissions`, `role_permissions`) stay without policies. `roles` needs `tenant_id IS NULL OR tenant_id = setting`.
- Blockers before enabling:
  - (1) the login path reads `memberships` before a tenant is known; it needs a narrow `SECURITY DEFINER` function or a separate auth role (M1);
  - (2) every request and background job must run through a tenant-scoped transaction (M1/M2/M3);
  - (3) the app must connect as the non-owner `amsc_app` (M7). Owners and superusers bypass RLS unless `FORCE` is set, and superusers always bypass it.
- Enabling RLS before (1) and (2) would break login on the day M7 switches the role. That is why it is not in 0009.
